# Quick Start

## Two repos, one workflow

| Repo | What it is | Who it's for |
|---|---|---|
| [`glen`](https://github.com/SchmidtDSE/glen) | glen core and its plugins: map, map tools, MCP, charts. Loaded from CDN. | Library contributors; this docs site. |
| [`glen-template`](https://github.com/SchmidtDSE/glen-template) | Starter template. Three files to edit, then deploy. | App builders — **start here**. |

**To build a new map app:** use the template. You never touch the library repo.

::: tip A map of public data needs no repository
The [map builder](./map-builder) makes an app of any public STAC or Portolan catalog in a form, and our sites run it: on GitHub Pages with each visitor's own key, or on NRP with its models. Start from the template when an app needs private data, its own server-side key, custom plugins or its own domain.
:::

## Start from the template

Go to [SchmidtDSE/glen-template](https://github.com/SchmidtDSE/glen-template) and click **Use this template → Create a new repository**. You get a ready-to-deploy repo with the three files you need. Edit them for your dataset and deploy.

**Live demo:** <https://schmidtdse.github.io/glen-template/>

## Your app is just three files

```
index.html          ← HTML shell — loads glen core JS/CSS from CDN
layers-input.json   ← which datasets to show, which plugins, how to connect to the LLM
system-prompt.md    ← what the data is and who the app is for
```

No JavaScript to write. glen core (the map and its tools) and its plugins load from jsDelivr, and the agent and chat come from [glen-harness](https://github.com/SchmidtDSE/glen-harness), which glen core loads itself.

## index.html

The HTML shell needs only glen core's `main.js` from the CDN, and two placeholder `<div>`s in the `<body>`; the layout manager builds the rest (chat panel, controls, etc.) dynamically. From v4.5.0, glen core adds the libraries it needs as page-global `<script>` tags itself (MapLibre, PMTiles, marked, DOMPurify and highlight.js), each with its pinned version and integrity hash, and glen's stylesheets before the page's own (`docs/design/page-dependencies.md`). There is no import map, and the MCP plugin loads a pre-bundled MCP SDK, so the only hosts your page contacts are the CDNs.

::: warning Copy this file from the template — don't hand-author it
The canonical `index.html` is `core/index.html` in this repository, as glen-template uses it. Copy it rather than retyping it. The block below matches the template at the pinned release.
:::

```html
<!DOCTYPE html>
<html lang="en">

<head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    <title>My Map App</title>

    <!-- glen core adds MapLibre, PMTiles, the chat's libraries and glen's
         stylesheets itself, with their integrity hashes. An app's own
         stylesheet goes here, after them. -->
    <style>
        /* Boot placeholder — see #boot-status in the body. */
        #boot-status {
            position: absolute;
            top: 50%;
            left: 50%;
            transform: translate(-50%, -50%);
            font: 14px/1.4 system-ui, sans-serif;
            color: #666;
            text-align: center;
        }
        #map.maplibregl-map #boot-status { display: none; }
    </style>
</head>

<body>
    <!-- Map -->
    <!-- #boot-status makes a failed module load read as "stuck loading" rather
         than an unexplained blank page. MapLibre puts .maplibregl-map on this
         container once the map exists, which hides it again — no JS needed (#343). -->
    <div id="map">
        <div id="boot-status">Loading map modules…</div>
    </div>

    <!-- Layer controls — generated by MapManager.generateMenu() -->
    <div id="menu"></div>

    <!-- GLEN bootstrap (pinned) -->
    <script type="module" src="https://cdn.jsdelivr.net/gh/SchmidtDSE/glen@v4.5.0/core/main.js"></script>
</body>

</html>
```

A page made for an earlier release lists the libraries and glen's three stylesheets itself. It keeps working unchanged: glen core leaves alone any library or stylesheet the page already has.

### About the `integrity` hashes

Each third-party script and stylesheet glen core adds carries an `integrity="sha384-…"` attribute — that's [Subresource Integrity (SRI)](https://developer.mozilla.org/en-US/docs/Web/Security/Subresource_Integrity). The browser downloads the file, hashes it, and **refuses to run it unless the hash matches**. If a CDN were ever compromised and served a tampered library, the mismatch blocks the swapped-in code instead of executing it. This matters here specifically because the agent renders model output (which can be steered by attacker-controllable data) into the page — DOMPurify sanitizes it, and SRI guarantees the *real* DOMPurify is the thing that loaded. `crossorigin="anonymous"` is required for SRI to work on cross-origin files.

**You never touch these values.** They live in glen: MapLibre and PMTiles in `core/boot.js` (`PAGE_SCRIPTS`, `PAGE_STYLESHEETS`), and marked, DOMPurify and highlight.js in glen-harness's `ui/deps.js` (`CHAT_SCRIPTS`). Bumping glen's pin brings the versions that release was tested with.

To use another version of a library, list it in the page yourself, with its own `integrity` and `crossorigin="anonymous"`; glen core then leaves it alone. A new version is different bytes, so it needs its own hash:

```bash
curl -sL "<the pinned URL>" | openssl dgst -sha384 -binary | openssl base64 -A
# prefix the result with "sha384-"
```

Pin an *exact* version (never a floating range like `@18` or bare `marked`), so the served bytes and the hash stay the same.

| CDN reference | When to use |
|---|---|
| `@vX.Y.Z` (e.g. `@v4.0.0`) | Every deployed app — pinned, immutable |
| `@<40-char-commit-sha>` | Short-lived demo of an in-flight feature branch |

`@main` is **not** used by deployed apps: a merge to `main` can change behavior under a running page, and tooling/MCP contracts evolve between releases. Bump the pin deliberately, never implicitly.

## layers-input.json

Minimal example:

```json
{
  "catalog": "https://s3-west.nrp-nautilus.io/public-data/stac/catalog.json",
  "collections": ["cpad-2025b"],
  "plugins": [
    { "url": "https://cdn.jsdelivr.net/gh/SchmidtDSE/glen@v4.0.0/core/plugins/mcp.js",
      "options": { "url": "https://duckdb-mcp.nrp-nautilus.io/mcp", "prompt": "geospatial-analyst" } }
  ],
  "llm": {
    "user_provided": true,
    "default_endpoint": "https://openrouter.ai/api/v1"
  }
}
```

Without `plugins`, the agent works the map alone: it shows, filters and styles layers from the catalog's metadata. The MCP plugin adds SQL queries over the data behind each layer. See [Configuration Reference](./configuration) for all fields and the other plugins.

## system-prompt.md

Plain Markdown, added after glen core's short base prompt. Tell the assistant what data it's looking at and who the app is for. Keep it short: the tools describe themselves. See [System prompt](./configuration#system-prompt).

```markdown
This app is for exploring California's protected lands: who owns
and manages them, and how well they are protected for biodiversity.
```

## Local development

```bash
# From your app folder (index.html + layers-input.json + system-prompt.md)
python -m http.server 8000
# Open http://localhost:8000
# Enter your API key in the ⚙ settings panel
```
